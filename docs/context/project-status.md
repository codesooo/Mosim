# 프로젝트 현재 상태

> 마지막 갱신: 2026-11-08. 상황이 바뀌면 사람이 갱신한다. AI는 바뀐 점을 알리기만 한다.
> 서비스 기획 원본: 프로젝트 문서 `claude/모심_서비스_기획.md`

## 1. 서비스 한 줄 정의

**모심: 동승자를 미리 이해하고, 차량과 이동 환경을 선제적으로 준비하는 에스코트 서비스.**
상사, 가족, 연인, 거래처 같은 동승자를 모시는 운전자가 출발 전부터 도착까지 필요한 준비를 놓치지 않게, 앱이 대신 판단하고 수행한다.

핵심 인사이트: 동승자가 탄 뒤에는 주유, 정비, 경로 변경이 어렵다. 그래서 **출발 전 판단**이 가장 중요하다.

설계 원칙: 동승자가 탄 뒤에는 운전자의 화면 조작을 최소화한다.

## 2. 이용 흐름 (7단계)

| # | 단계 | 모드 | 화면 | 핵심 |
|---|---|---|---|---|
| 01 | 동승자 선택 | 운전자 | 있음 | 프로필 + 픽업지·목적지 |
| 02 | 출발 전 차량 점검 | 운전자 | 있음 | 현재 상태와 예정 이동을 비교해 필요한 행동 판단 |
| 03 | 픽업 전 실내 준비 | 운전자 | 있음 | 개인화 값을 차량에 적용(원터치) |
| 04 | 탑승 감지 | 전환 | 있음 | 착석 + 벨트 + 도어 열림→닫힘 + 정차 → 에스코트 모드 |
| 05 | 이동 중 선제 케어 | 에스코트 | **없음** (데이터만 기록) | 온도·좌석·음악 조절 |
| 06 | 상황 변화 대응 | 에스코트 | 최소 | 음성 요청 처리 (예: 근처 카페) |
| 07 | 도착·프로필 업데이트 | 종료 | 최소 | 하차 감지 → 자동 종료 + 데이터 저장 |

개인화 저장 규칙: 설정 온도는 **반드시 당시 외기 온도와 쌍으로** 저장한다.

온도 추천 공식(초안, 미확정): `추천온도 = 과거 설정온도 − k × (현재 외기 − 과거 외기)`, k = 0.1, 결과는 18~28°C로 제한.

## 3. 코드베이스 현황

- Android 앱, Kotlin + Jetpack Compose + Material3, 단일 `app` 모듈.
- 확정 버전은 `README.md`의 표를 따른다(JDK 17, AGP 8.13.0, Kotlin 2.2.20, compileSdk 36, targetSdk 35, minSdk 28).
- 화면: 이동 경로 확인용 **임시 화면**만 있다. 메인 화면의 버튼 네 개로 각 화면에 들어간다.
- 차량 데이터: 전부 Mock이다.
  - `platform/pleos/VehicleStatusSource.kt` — 화면이 보는 인터페이스
  - `data/mock/MockVehicleStatusSource.kt` — 현재 쓰는 Mock
  - `platform/pleos/PleosVehicleStatusSource.kt` — 실제 SDK 연동 자리, 비어 있음
  - `platform/pleos/VehicleStatusSourceProvider.kt` — `USE_MOCK`로 교체
- `docs/requirements.md`는 **비어 있다.** 팀이 채운다.
- 와이어프레임 미확정.

## 5. 검토 중 (팀 결정 필요)

- **Agentic AI 오케스트레이션(REQ-008)**: 단일 에이전트 + 여러 Tool 구조로, 동승자 프로필·차량 상태·경로·날씨를 Tool로 조회하고 실행 계획을 세우는 안.
  기존 결정 "의도 파악 보류"와 충돌한다. 어떤 LLM을 쓸지도 정해지지 않았다(Pleos LLM SDK는 종료).
  **팀 결정 전까지 LLM 호출 코드는 쓰지 않는다.** Tool 인터페이스와 Mock은 다른 기능에도 쓰이므로 만들어도 된다.
  검토 문서에서 정한 안전 규칙은 이 안을 채택하면 그대로 적용한다.
  - 정의된 Tool만 제공하고 임의 코드 실행은 금지
  - 확정 계산(주행거리 부족 등)은 일반 코드로 판단
  - 차량 상태를 바꾸는 행동은 안전 조건과 운전자 승인 후 실행. 승인은 출발 전이나 정차 중에
  - 성공, 실패, Mock 실행을 구분해 기록
  - 호출 횟수와 실행 시간 제한
